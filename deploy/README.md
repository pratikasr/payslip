# Hosting Payslip on AWS

One EC2 instance runs the whole thing with Docker Compose; two CloudFront distributions put TLS
and a public address in front of it. The public statements page (`books`) serves judges,
contractors and accountants with the judge kit; the company console (`app`) is behind HTTP Basic
auth until the sign-in layer lands. Every AWS resource is created by a script you run on your own
machine with your own credentials, and removed by its twin.

| Address | What | On the instance |
| --- | --- | --- |
| `https://<books>.cloudfront.net` | landing page, `/books`, `/portal`, `/verify` | `books-web` (Next.js) on port 3001 |
| `https://<books>.cloudfront.net/api/*` | statements, reconciliation, payment proofs | `books-service` (`PAYSLIP_MODE=statements`, no seed) on port 8081 |
| `https://<app>.cloudfront.net` | company console, basic auth | `app-web` on port 3002 |
| `https://<app>.cloudfront.net/api/*` | full service: wallet, contractors, runs | `app-service` (seed and spending keys) on port 8082 |

The four ports belong to `caddy`, a plain HTTP front that passes each request to the right
container after checking the origin secret (below). The application containers publish nothing.
Both services keep their data in named Docker volumes (`payslip_books-data`, `payslip_app-data`):
the age-encrypted seed, `wallet.db`, `payslip.db` and the viewer scan caches.

Files in this directory:

| File | Purpose |
| --- | --- |
| `aws/provision.sh` | creates the AWS resources and writes `aws/outputs.env` (git-ignored) |
| `aws/destroy.sh` | removes them by tag |
| `install.sh` | prepares the Ubuntu 24.04 instance: Docker, AWS CLI, UFW, fail2ban, unattended upgrades, age, swap, the nightly backup job |
| `compose.yml`, `Caddyfile` | the five containers and the HTTP front |
| `Dockerfile.service`, `Dockerfile.web` and their `.dockerignore` files | the two images |
| `payslip.env.example` | every variable the compose file reads, copied to `payslip.env` (git-ignored) |
| `backup.sh` | encrypted archives of both data volumes to S3 |

## What protects the company service

The full-mode service has no login of its own, so the layers in front of it are the security
model. From the outside in:

1. **CloudFront with HTTP Basic auth.** A CloudFront Function on the `app` distribution answers
   401 unless the request carries the credentials `provision.sh` embedded in it (base64 of
   `user:password`; the password is asked for once and is not stored anywhere else). Every
   request to `app`, pages and `/api/*` alike, passes this check. The `books` distribution has no
   such check: a statements-only service holds nothing that can spend.
2. **The security group.** The instance accepts 22/tcp from the address `provision.sh` was run
   from, and 3001 to 8082/tcp from the CloudFront origin-facing prefix list only. That is one
   rule for the whole range because the managed list weighs 55 of the 60 rules a security group
   may hold (AWS VPC user guide, checked 11 Oct 2026); only the four ports listen.
3. **The origin secret.** Any AWS customer can point a CloudFront distribution at this instance,
   and such traffic also comes from CloudFront's ranges. So each distribution adds a custom
   origin header `X-Payslip-Origin: <secret>` to every request (this is the AWS-documented way to
   restrict a custom origin to your own distributions), and `Caddyfile` answers 403 to any
   request without it. The secret is generated by `provision.sh`, kept in `aws/outputs.env`, and
   copied into `payslip.env` on the instance.
4. **The Host allowlist.** The service answers 421 for any `Host` other than its distribution's
   name, the instance's own DNS name and its compose name (`PAYSLIP_ALLOWED_HOSTS`).
5. **Loopback by default.** In full mode the service refuses to listen on anything but
   127.0.0.1 unless `PAYSLIP_ALLOW_REMOTE_PAYER=1`. The compose file sets it, because inside a
   container "remote" means the compose network: the only peers are `caddy` (which enforces 3)
   and `app-web` (its server-side reads). The container's port is not published on the instance.
6. **The host.** UFW allows 22 and the four ports, fail2ban watches sshd, security updates
   install themselves, IMDSv2 is required, the instance role can only write to the backup bucket.

What this does not give you: per-user accounts, roles or an audit trail (the sign-in increment
in `docs/superpowers/specs/2026-10-11-launch-plan-design.md` adds those), and the basic-auth
comparison in the CloudFront Function is a plain string comparison. Keep the custody rule from the
README: the treasury holds what one run needs, for minutes.

## What stays private

Never in the repository, never in a chat, never on a shared screen:

- `PAYSLIP_SEED_PASSPHRASE` and the seed file `payer.seed.age` (inside `payslip_app-data`). The
  two together are the only way back to the treasury; `init` shows no recovery phrase.
- The data volumes and their backups (they hold the seed and every viewing key ever pasted).
- `deploy/payslip.env` and `deploy/aws/outputs.env` (the origin secret). Both are git-ignored.
- The age private key for backups (`payslip-backup.key`), kept on your machine and in a password
  manager; only the public key goes on the server.
- The SSH private key and the console password.

The viewing keys published in the judge kit are the exception, on purpose: that wallet is a demo.

## Before you start

On your machine: the AWS CLI v2 configured with a profile that may create EC2, VPC security
groups, IAM roles, S3 buckets and CloudFront resources (`AWS_PROFILE`; the region comes from
`AWS_REGION`, default `us-east-1`), `curl`, `python3`, `openssl`, `git`, `ssh`, and the SSH key
pair at `~/.ssh/payslip-hetzner` and `~/.ssh/payslip-hetzner.pub` (another public key:
`SSH_PUBKEY=path`). Also `age` (`brew install age`) for the backup key.

The default VPC of the region must exist (`aws ec2 create-default-vpc` recreates it).

## 1. Provision

```
export AWS_PROFILE=<your profile> AWS_REGION=us-east-1
deploy/aws/provision.sh
```

It asks once for the console password (12 or more characters, user `payslip`; set
`APP_BASIC_AUTH_USER` and `APP_BASIC_AUTH_PASSWORD` to skip the prompt), then creates, in this
order and tagged `Project=payslip` and `Stack=payslip`: the key pair, the security group, the
backup bucket, the instance role, the instance (`INSTANCE_TYPE`, default `t3.small`; `t3.medium`
builds faster and has room for both services without swapping), the Elastic IP, the CloudFront
function and the two distributions. It prints the two CloudFront host names and the IP, and
writes them with the origin secret to `deploy/aws/outputs.env` (mode 600).

Run it again at any time: it finds what exists and completes what is missing. If your public IP
changed, it adds a new SSH rule (remove the old one with `aws ec2 revoke-security-group-ingress`).
To change the console password: `ROTATE_APP_AUTH=1 deploy/aws/provision.sh`.

The distributions take a few minutes to reach `Deployed`:

```
. deploy/aws/outputs.env
aws cloudfront get-distribution --id "$BOOKS_DISTRIBUTION_ID" --query Distribution.Status --output text
```

## 2. Copy the repository to the instance

The repository is private, so ship it from your machine. Committed files only, no secrets, no
build directories:

```
. deploy/aws/outputs.env
git archive --format=tar HEAD | ssh -i ~/.ssh/payslip-hetzner ubuntu@"$INSTANCE_IP" 'mkdir -p payslip && tar -x -C payslip'
```

(To ship uncommitted work instead: `rsync -az --delete --exclude .git --exclude '.env' --exclude '.env.*' --exclude '*.env' --exclude service/target --exclude service/data --exclude web/node_modules --exclude web/.next --exclude scripts/demo/out -e 'ssh -i ~/.ssh/payslip-hetzner' ./ ubuntu@"$INSTANCE_IP":payslip/`. The exclusions keep every local env file, including `scripts/demo/mainnet.env`, off the server.)

## 3. Install the host software

```
ssh -i ~/.ssh/payslip-hetzner ubuntu@"$INSTANCE_IP"
sudo payslip/deploy/install.sh
exit
```

Then log in again so that `ubuntu` is in the `docker` group.

## 4. Configure

On the instance:

```
cd ~/payslip/deploy
cp payslip.env.example payslip.env
chmod 600 payslip.env
nano payslip.env
```

Fill in, from `deploy/aws/outputs.env` on your machine: `BOOKS_HOST`, `APP_HOST`, `INSTANCE_DNS`,
`ORIGIN_SECRET`, `BACKUP_BUCKET`, `AWS_REGION`. Then `ZCASH_NETWORK`, a new
`PAYSLIP_SEED_PASSPHRASE` (12 or more characters; single quotes around it if it contains `$`, `#`
or spaces; a copy in your password manager now), and `BACKUP_AGE_RECIPIENT`:

```
age-keygen -o ~/payslip-backup.key          # on your machine; the public key is on the line "# public key: age1..."
```

For the testnet judge kit set `PAYSLIP_VIEWER_BIRTHDAY_HEIGHT=4466850` (just below the demo
wallet's birthday, so the first scan is short). On mainnet set it just below the mainnet demo
wallet's birthday once `scripts/mainnet-demo.sh` has printed it. Check the rendered file:

```
docker compose --env-file payslip.env config >/dev/null && echo ok
```

## 5. Build and start

One image at a time; the service image is the long step and both service containers share it:

```
docker compose --env-file payslip.env build books-service
docker compose --env-file payslip.env build books-web
docker compose --env-file payslip.env build app-web
```

Create the company wallet (prints the treasury address) and back it up before any money moves:

```
docker compose --env-file payslip.env run --rm app-service init
sudo ./backup.sh
```

Start everything and check it:

```
docker compose --env-file payslip.env up -d
docker compose --env-file payslip.env ps
SECRET=$(sed -n 's/^ORIGIN_SECRET=//p' payslip.env)
curl -s -H "X-Payslip-Origin: $SECRET" http://127.0.0.1:8081/api/health     # books service, through caddy
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8081/api/health     # 403: the gate works
```

From your machine, once the distributions are `Deployed`:

```
. deploy/aws/outputs.env
curl -s "https://$BOOKS_HOST/api/health"
curl -s -u payslip "https://$APP_HOST/api/health"
```

`mode` is `statements` on the first and `full` on the second. Open `https://$BOOKS_HOST/books`,
choose Import key file and pick the judge kit (`docs/judge/judge-kit-testnet.json` in the
repository; the same file is served at `https://$BOOKS_HOST/judge-kit-testnet.json`). The
mainnet kit goes the same way once it exists: copy `docs/judge/judge-kit-mainnet.json` to
`web/public/`, ship, `build books-web`, `up -d books-web`.

Logs: `docker compose --env-file payslip.env logs -f app-service`.

## Two networks

One stack serves one network (the data volumes and the fixed-rate testnet venue are per network).
For the testnet judge kit and a mainnet page at the same time, make a second stack:

```
STACK=testnet deploy/aws/provision.sh        # writes deploy/aws/outputs-testnet.env
```

and repeat steps 2 to 5 on that instance with `ZCASH_NETWORK=testnet`.

## Update

On your machine, ship the new revision (step 2). On the instance, keep the running images as a
rollback point, rebuild what changed, and restart:

```
cd ~/payslip/deploy
for i in payslip-service payslip-web-books payslip-web-app; do docker tag "$i:local" "$i:previous"; done
docker compose --env-file payslip.env build books-service     # only the images whose sources changed
docker compose --env-file payslip.env build books-web app-web
docker compose --env-file payslip.env up -d
```

Service migrations run on start (sqlx). A change to `BOOKS_HOST`, `APP_HOST` or
`NEXT_PUBLIC_*` needs the web images rebuilt, because those values are inlined at build time.

## Roll back

```
for i in payslip-service payslip-web-books payslip-web-app; do docker tag "$i:previous" "$i:local"; done
docker compose --env-file payslip.env up -d --no-build
```

The data volumes are untouched by a rollback. A migration that the older service does not know
is the one case to check first: `docker compose --env-file payslip.env logs app-service`.

## Backups and restore

`install.sh` runs `backup.sh` every night at 03:17 UTC (`/etc/cron.d/payslip-backup`, log in
`/var/log/payslip-backup.log`); run it by hand with `sudo ./backup.sh`. Each run pauses a service
for the seconds its volume takes to archive, encrypts the archive to `BACKUP_AGE_RECIPIENT`, and
uploads it to the bucket under a UTC time stamp, for example
`20261011T031700Z/payslip_app-data-20261011T031700Z.tar.gz.age`, with the instance role (no AWS keys on the host). Public access to the bucket is blocked.

List, fetch the newest archive of the company volume and decrypt it, on your machine:

```
. deploy/aws/outputs.env
aws s3 ls "s3://$BACKUP_BUCKET/"
KEY=$(aws s3api list-objects-v2 --bucket "$BACKUP_BUCKET" --query 'sort_by(Contents[?contains(Key, `payslip_app-data`)], &LastModified)[-1].Key' --output text)
aws s3 cp "s3://$BACKUP_BUCKET/$KEY" .
age -d -i ~/payslip-backup.key "$(basename "$KEY")" > payslip_app-data.tar.gz
```

Restore on the instance (the archive decrypted on your machine, copied over with `scp`):

```
cd ~/payslip/deploy
docker compose --env-file payslip.env stop app-service
docker run --rm -v payslip_app-data:/data -v "$PWD":/restore alpine:3.20 sh -c 'rm -rf /data/* /data/.[!.]* && tar -C /data -xzf /restore/payslip_app-data.tar.gz'
docker compose --env-file payslip.env start app-service
rm payslip_app-data.tar.gz
```

The same with `books-service` and `payslip_books-data`. An older `wallet.db` is fine: the service
rescans from its birthday. What cannot be rebuilt is `payer.seed.age`, so keep more than one copy
of the archives and of the passphrase.

## Attach a real domain later

Nothing above needs a domain. When you have one (Route 53 as the DNS host; CloudFront only
accepts certificates from ACM in `us-east-1`), with `payslip.cash` as the example:

1. Hosted zone, then the four name servers it prints go to the registrar:
   ```
   DOMAIN=payslip.cash
   ZONE_ID=$(aws route53 create-hosted-zone --name "$DOMAIN" --caller-reference "$(date +%s)" --query HostedZone.Id --output text)
   aws route53 get-hosted-zone --id "$ZONE_ID" --query DelegationSet.NameServers --output text
   ```
2. Certificate for both names, validated by DNS records that ACM names:
   ```
   CERT_ARN=$(aws acm request-certificate --region us-east-1 --domain-name "books.$DOMAIN" --subject-alternative-names "app.$DOMAIN" --validation-method DNS --query CertificateArn --output text)
   sleep 10
   aws acm describe-certificate --region us-east-1 --certificate-arn "$CERT_ARN" --query 'Certificate.DomainValidationOptions[].ResourceRecord' --output table
   ```
   Create each `CNAME` it lists in the hosted zone (`aws route53 change-resource-record-sets`, as
   in step 4 with `"Type":"CNAME"` and a `ResourceRecords` value instead of an alias), then
   `aws acm wait certificate-validated --region us-east-1 --certificate-arn "$CERT_ARN"`.
3. Each distribution: fetch its config, add the alias and the certificate, submit it back.
   ```
   . deploy/aws/outputs.env
   for pair in "books:$BOOKS_DISTRIBUTION_ID" "app:$APP_DISTRIBUTION_ID"; do
     name=${pair%%:*}; id=${pair#*:}
     aws cloudfront get-distribution-config --id "$id" > "dist-$id.json"
     etag=$(python3 -c 'import json,sys; print(json.load(open(sys.argv[1]))["ETag"])' "dist-$id.json")
     python3 - "dist-$id.json" "$name.$DOMAIN" "$CERT_ARN" <<'PY'
   import json, sys
   path, alias, cert = sys.argv[1:]
   d = json.load(open(path))["DistributionConfig"]
   d["Aliases"] = {"Quantity": 1, "Items": [alias]}
   d["ViewerCertificate"] = {"ACMCertificateArn": cert, "SSLSupportMethod": "sni-only", "MinimumProtocolVersion": "TLSv1.2_2021"}
   json.dump(d, open(path + ".update", "w"))
   PY
     aws cloudfront update-distribution --id "$id" --if-match "$etag" --distribution-config "file://dist-$id.json.update" >/dev/null
   done
   ```
4. DNS: an alias `A` and `AAAA` record per name to its distribution. The hosted zone id of
   every CloudFront distribution is `Z2FDTNDATAQYW2` (Route 53 API reference, AliasTarget).
   ```
   for pair in "books:$BOOKS_HOST" "app:$APP_HOST"; do
     name=${pair%%:*}; target=${pair#*:}
     for type in A AAAA; do
       aws route53 change-resource-record-sets --hosted-zone-id "$ZONE_ID" --change-batch "{\"Changes\":[{\"Action\":\"UPSERT\",\"ResourceRecordSet\":{\"Name\":\"$name.$DOMAIN\",\"Type\":\"$type\",\"AliasTarget\":{\"HostedZoneId\":\"Z2FDTNDATAQYW2\",\"DNSName\":\"$target\",\"EvaluateTargetHealth\":false}}}]}"
     done
   done
   ```
5. On the instance: `BOOKS_HOST=books.payslip.cash` and `APP_HOST=app.payslip.cash` in
   `payslip.env`, the two `*.cloudfront.net` names in `EXTRA_ALLOWED_HOSTS` if they should keep
   working, then rebuild both web images (the portal address is inlined) and `up -d`.

## Destroy

```
deploy/aws/destroy.sh                   # keeps the backup bucket
deploy/aws/destroy.sh --delete-backups  # removes the bucket and every archive too
```

It lists what it found by tag, asks for the stack name, disables and deletes the distributions
(the disable must deploy first, a few minutes each), then the function, the instance, the
Elastic IP, the security group, the key pair and the IAM role. The instance's volumes go with it:
take a backup first.

## Known limits

- CloudFront waits at most 120 seconds for the origin (the account default; the distributions
  are set to it). A first scan of a key from a very old birthday can take longer and answers
  504; the service keeps what it scanned, so a retry continues. Setting
  `PAYSLIP_VIEWER_BIRTHDAY_HEIGHT` near the wallet's birthday avoids this.
- Run progress streams (SSE) pass through CloudFront with the service's 15-second keep-alives.
- A `t3.small` (2 GB) runs everything with the swap file `install.sh` adds; the company service
  peaks near 1 GB after start. If `docker stats` shows `app-service` at its limit, move to
  `t3.medium` (`INSTANCE_TYPE=t3.medium`; a new stack, then restore the backup).
- The service image build compiles the Zcash crates with one job by default
  (`CARGO_BUILD_JOBS=1`); on a bigger instance raise it in `payslip.env`.
